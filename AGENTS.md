# Architecture
- Use request-time USDA secrets in server-only request headers for manual, hybrid and AI ingredient searches; protect personal-quota calls with auth and return setup state only to avoid browser or URL credential exposure.
- Keep food AI credentials in a request-time server-only configuration helper; authenticated setup checks return only configuration state, and a real estimate—not key presence—establishes live validation.
- Declare allowlisted environment variable names as preview-only Cloudflare worker secrets so supervisor credentials reach request-time handlers without copying values into files, browser defines, or production build configuration.
- Test nutrition server-function validators and handlers with a lightweight RPC-builder mock and mocked external responses; keep real signed-in logging checks separate so simulated AI success is never mistaken for provider verification.
- Keep numeric editing drafts in the shared Input, separate from parsed form values, so signed decimals, clearing, and pasted precision survive rerenders without native steppers.
- Store optional per-meal goals separately from daily net-calorie targets; share owner-scoped query hooks and a picker across search modes so meal calories remain gross intake and blank nutrients stay unset.
- Reuse the same meal-goal editor in Profile and the Dashboard Food log dialog so saved targets and validation remain consistent.
- Create the shared query client per root mount, never in a module global, to isolate SSR requests and support meal-goal queries.
- Build with the Cloudflare Vite plugin and its `ssr` environment, not Nitro's Vercel preset, so Lovable receives the deployable `dist/` output.
- Resolve allowlisted public auth values in configResolved after Vite loads settings, with checked-in public connection defaults for isolated builds; preserve wrapper overrides in client and SSR and reject missing/private keys without serializing the full environment.
- Keep map restaurant discovery separate from the existing chain-combo search so each retains its single-dish or multi-item ranking contract.
- Call Google Places and menu scraping only from authenticated server functions; keep credentials server-side and cap restaurant search to 12 results and menu retrieval to two pages per explicit action.
- Cache only website-derived menu estimates in an owner-scoped table, not Google place content; this avoids repeated paid estimates while preserving Google attribution.
- Rank restaurant dishes at their standard serving size by summed normalized absolute distance over supplied targets; never scale restaurant portions or combine dishes in this flow.
- Register browser bearer attachment in src/start.ts so protected server functions validate signed-in callers.
- Use request-scoped Responses AI SDK calls with streaming, strict output schemas and gateway run IDs; provider denials remain durably paused until service access is restored.
- Keep nutrition evidence scoring in a shared pure module; cite only retrieved records or provided labels/menu excerpts, persist evidence with logged items, and distinguish evidence scores from calibrated accuracy probabilities to prevent unsupported precision.
- Present evidence as five categorical confidence levels while retaining stored scores and legacy enums; this improves readability without claiming calibrated probabilities or migrating saved estimates.
- Represent complex meals as one parent with nested ingredient evidence; sum inferred ingredient totals once, preserve published meal totals separately, and invalidate breakdowns after manual parent edits to avoid double counting or stale contributions.
- Keep hybrid single-food search database-only with explicit record selection; use shared pure diary-editing functions for proportional portions, ingredient totals and atomic meal moves so edits cannot duplicate intake.
